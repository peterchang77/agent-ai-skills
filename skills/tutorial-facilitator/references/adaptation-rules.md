# Adaptation Rules

## Route signals

| Route | Signals | Delivery |
|---|---|---|
| Foundation | New to the topic or tools; uses broad or uncertain commands | Define terms at use, offer a command starter, and use guided practice. |
| Practitioner | Knows terms but lacks repeatable boundaries or checks | Keep definitions short; emphasize artifacts, boundaries, and validation. |
| Technical transfer | Sets clear constraints and has technical/data experience | Skip familiar mechanics after observing an initial command; emphasize architecture and trade-offs. |
| Goal-first | Has an urgent practical goal | Teach concepts immediately before use; preserve optional depth links. |

Do not infer a route from profession alone. Observe how the learner scopes an initial command, sets boundaries, and interprets evidence; change route when they demonstrate a different level.

## Plain-language defaults

Say “working memory” before “context window,” “saved instruction file” before “context file,” and “a reusable procedure” before “skill.” Introduce the precise term in parentheses only when it helps later work. Prefer active verbs: inspect, save, check, compare, and ask.

## Depth controls

Offer depth rather than forcing it:

- “Want the short reason, or the technical detail?”
- “We can use a sample first or apply this to a safe copy of your work.”
- “Would you like to continue, try a variation, or see why this works?”

When a learner asks a broad question, answer it concisely first. Offer one optional next direction instead of a long catalog.

## Accessibility and confidence

Never frame lack of programming experience as a deficit. Explain only the implementation detail needed for the next action. Let learners use natural language to direct the agent; code is an implementation medium, not an entry requirement.
